# RunPod GPU Ops — pods, serverless, bootstrapping

Manage on-demand GPU compute for model-serving workloads. Standing user rules: never run ambient/always-on GPU work — spawn only in response to a user action, and rate-limit every endpoint that can cost money (per-IP token bucket + a global hourly cap at the relay, not on the GPU). Default posture: workers-min 0, execution timeout set, idle timeout short.

## Access & tooling

- `RUNPOD_API_KEY` lives in `~/.hermes/.env` (source with `set -a; source ~/.hermes/.env; set +a`). `runpodctl` is at `~/.local/bin/runpodctl`.
- REST v1 (`https://rest.runpod.io/v1/...`) is the reliable API. EVERY REST call needs `-H "User-Agent: Mozilla/5.0"` or Cloudflare returns error 1010. REST auth is `-H "Authorization: Bearer $RUNPOD_API_KEY"` — the bare key that GraphQL accepts returns empty/401 on REST. GraphQL accepts either form.
- The GraphQL API (`api.runpod.io/graphql`) has drifted: `pods`/`podCreate`/`podDeploy` may not exist; `podResume(input:{podId,gpuCount})` still works for starting a stopped pod. Introspection is disabled (validation errors name the valid fields — read them). Two queries that DO work: `query { myself { endpoints { id name workersMin workersMax gpuCount env { key value } } } }` and `query { gpuTypes { id displayName lowestPrice { minimumBidPrice uninterruptablePrice } } }` — the latter is the price check before choosing a GPU class. The endpoints query's `env { key value }` carries the worker's MODEL_NAME — the ONLY reliable way to identify which model an endpoint serves (`/v2/<ep>/health` shows worker counts but not the model), so check it before blaming output register on a model size. Prefer REST + runpodctl for everything else.
- GPU type IDs for REST `gpuTypeIds` use full official names — `NVIDIA RTX A6000`, `NVIDIA A40`, not `NVIDIA A6000`. Consumer cards carry the `GeForce` infix (`NVIDIA GeForce RTX 4090`, not `NVIDIA RTX 4090`) — pro cards don't; a wrong name returns the full enum in the error, read it.
- COMMUNITY-cloud pod CREATES need `supportPublicIp: true` in the REST body — the same constraint runpodctl exposes as `--public-ip` — or the create bounces schema validation even when every other field is right.
- REST create body shape: the image key is `imageName` (NOT `image`), `gpuTypeIds` is an ARRAY of full-name strings (`["NVIDIA A40"]`, not a bare string — the schema error names the key and the wanted type), `dockerStartCmd` is an ARRAY (`["bash", "-c", script]`), `ports` is an array of strings (`["8000/http"]`), `env` is an object, `cloudType` is `SECURE` or `COMMUNITY` only. Schema validation errors list the exact offending key — follow them. runpodctl flag names differ from REST keys: `--container-disk-in-gb` (not `--container-disk`), `--env` takes ONE JSON-object string, and `--wait` on COMMUNITY also needs `--public-ip`.
- Image choice: `runpod/pytorch:*` tags have disappeared from the registry ('not found on the registry'); the official `pytorch/pytorch:2.8.0-cuda12.8-cudnn9-runtime` image works on RunPod and carries torch — only pip-install the rest in the boot script.
- Small payload shipping (<~100KB, scripts + small data): skip the tunnel entirely — base64 the tarball into the boot script (`echo <B64> | base64 -d > payload.tgz; tar xzf payload.tgz`). When shipping an adapter directory as a tarball, tar the DIRECTORY (`tar czf x.tgz mydir/` from its parent), not its contents from inside it — a contents-tar extracts flat into the target and every `adapter_config.json` check fails while the extract itself succeeds. Private repos are unreadable from the pod; embed or tunnel anything not public.
- Loading a PEFT adapter for inference: `PeftModel.from_pretrained(base, adapter_dir)` — the raw constructor `PeftModel(base, adapter_dir)` dies with `AttributeError: 'str' object has no attribute 'peft_type'` because the constructor's second argument is a PeftConfig, not a path.
- Boot scripts that pip-install the HF stack must resolve to the SAME VERSIONS as a KNOWN-GOOD environment — but never guess the pins: read them out of the working run's own log (a training pod's train.log prints the transformers version it used) or copy the working run's exact install command verbatim, and write a `python3 -c "import transformers, huggingface_hub; print(versions)"` line into boot.log before the real runner so a bad resolve is visible in one glance. Two failure classes from pinning wrong, both hit in one debug session: (1) pinning a LOCAL combo onto a NEWER image breaks imports — an image shipping transformers 5.x needs huggingface_hub >=1.31, and pinning hub 0.36 dies at `ImportError: ResolvedRevision`; (2) the image's fresh unpinned resolve can pull a BROKEN downloader — hub 1.x with httpx2 crashes large downloads (`TypeError: process() takes no keyword arguments`) while hub+httpx 0.28 works. So pin IN ORDER (transformers first to keep the image's version, then the hub range it needs), and verify BOTH imports (`import transformers, huggingface_hub`) AND a real download (`hf_hub_download` of one small file) in the boot before the real runner — a version set that imports but cannot download wastes a full model-fetch on the GPU clock. Architecture gates the version from below: model_type `qwen3_5` (Qwen3.5-generation) needs transformers ≥5.19 — 4.x dies with 'does not recognize this architecture' at AutoConfig time. transformers 5.x also removed `load_in_8bit` as a from_pretrained kwarg - pass `quantization_config=BitsAndBytesConfig(load_in_8bit=True)`. If a boot crashes twice on dependency clashes, stop pip-on-boot and bake a pushed image. Also: one `pip install` invocation is atomic — a single unbuildable package (anything needing nvcc, like causal-conv1d) aborts the WHOLE line and the runner dies at the first import; put optional speedups on a SEPARATE line with `|| true`. RunPod RESTARTS the container whenever dockerStartCmd exits nonzero — a version crash presents as a healthy-looking pod looping `step 1` every few minutes in progress.log; read the repeating first step as a crash-loop, not slow progress.
- Self-terminating pod pattern for one-shot experiment runs — the DEFAULT shape, because flows that depend on interactive SSH are fragile: sshd/port-mappings on a fresh pod (even SECURE, even with a custom dockerStartCmd) frequently never come up while REST/GraphQL report RUNNING. Bake the whole job into `dockerStartCmd` (deps install → fetch payload from HF/tarball → run → write results → `python3 -m http.server 8888` in the results dir → `sleep infinity`), then run a LOCAL watcher loop that polls `https://<pod>-8888.proxy.runpod.net/<status-file>` every 60s, pulls the results the moment it returns 200, then PATCHes `desiredStatus: EXITED` (full body needs `name` + `desiredStatus`). The watcher also catches a crashed runner (traceback in the log 3 polls running) so the pod never idle-bills on a dead run — and VERIFY pulled results by first byte (jsonl must start with `{`), because the http.server returns a 404 HTML page for any missing path and a naive watcher saves that page as `results.jsonl` and reports success. A `done` status within ~3 minutes of pod creation means the boot died early (pip resolution failure, missing payload) — fetch run.log before celebrating. Fetching the proxy with python urllib gets 403 — the proxy rejects bare default UA strings; curl with a normal UA gets 200. mac `stat -f %z` does NOT follow symlinks — use `-L` when checking blob/file sizes via symlink chains. Timebox the watcher: an exhausted poll budget on a 502ing proxy means check `runpodctl pod logs` for whether the run is still downloading weights before re-arming another watcher loop — never leave a GPU pod billing unwatched overnight.
- Make the boot OBSERVABLE or debug blind: start the http.server and `touch` the log/status files BEFORE any work, drop `set -e`, and append a labeled line to boot.log after every step (pip-ok/adapter-ok/...) — a failing step in a `set -e` boot leaves the container flapping with zero `source:container` logs, and the only signal is a pod whose uptime resets every ~60s. Read the boot log through the proxy to triage without a redeploy. Proxy response semantics: a 502 'Waiting for service' page means the server is not up yet; a python http.server 404 error page means the server IS serving and the URL path is wrong — the server serves its CWD (start it in `/root` with results under `/root/out/` → they fetch at `/out/<file>` in the proxy URL).
- Linear-attention / hybrid-arch models (Qwen3.5-generation, Mamba-style) silently fall back to reference PyTorch kernels when `causal-conv1d` and `flash-linear-attention` are missing — transformers logs 'correct but much slower' and generation crawls (measured ~2.5x on a 27B). But the two packages fail DIFFERENTLY and neither is a plain pip fix: `flash-linear-attention` pip-installs fine and its TRITON kernels then die at runtime with 'Failed to find C compiler' — `pytorch/pytorch:*-runtime` images ship no compiler, so put `apt-get install -y gcc` in the boot before pip; `causal-conv1d` builds a CUDA extension and needs the full nvcc toolkit (multi-GB) for a minor conv op — install FLA, skip causal-conv1d, and put them on separate pip lines (`|| true`) so the unbuildable one cannot abort the other (pip install is atomic per invocation).
- Repeated pod deploys of the same model: attach a NETWORK VOLUME (`networkVolumeId` on create, `runpodctl network-volume create --name X --size N --data-center-id <dc>`) and point `HF_HOME` at a dir on it — the first pod downloads the weights into the volume, every later pod mounts the cache and skips the fetch. Without this, every crash-redeploy cycle re-downloads tens of GB of weights on the GPU clock (~30-40 paid minutes for a 27B each time), which is usually the single biggest waste in a crash-loop debug session. Volume and pod must share a datacenter — pods do not expose theirs via API, so create the volume in the DC you expect the GPU pool to land in and recreate on a create-time mismatch error.
- Standing pod shape for multi-experiment sessions: put BOTH the HF cache and the output dir on the network volume. Weights survive crash-redeploys and balance-death; artifacts no longer depend on the tailer catching them before a stop. Caveat: a network volume is only mountable by a pod — it is NOT readable from the Mac, so live log visibility still needs the HF tailer or the http.server proxy. Use both: volume for weights+artifacts, tailer for streaming. Cheap: an idle volume bills only storage (~$0.07/GB/mo), and it outlives every pod.
- Runner crash-safety vs the tailer: partial dumps must go to a DISTINCT filename (e.g. `results.partial.json`), never the final one — the tailer uploads every cycle and will commit a half-written `results.json` if the runner dumps in-place mid-write; a truncated upload reads as data corruption, not a crash. Write the final file atomically-once at the end; the final upload loop then overwrites any partial the tailer caught.
- Combining multiple one-shot experiments onto ONE pod: run them sequentially in one boot (each `python ... || log "FAILED"` so one failure never blocks the rest), all runners honoring the same `WC_OUT_DIR` so the tailer uploads rows as they are written. One 14B download serves several jobs — the model load dominates a short job's wall-clock, so batching is the single biggest cost lever for sub-30-minute runs. Give each job its own log file in the tailer's upload list.
- Watcher hygiene: a local `for`-loop watcher whose inner fetch is a python heredoc must not use `break` at the heredoc's top level — it SyntaxErrors on every poll while the loop keeps sleeping, reading as silence. Put the terminal-marker exit in the SHELL loop (`case "$R" in *TERMINAL*) break;; esac`), keep the python fetch break-free, and sanity-print each poll's fetched line so a dead watcher is visible immediately.
- When successive one-shot pods share ONE HF results repo, the tailers overwrite each other's files: every pod writes the same `progress.log`/`rank.log` paths, so a later pod clobbers the earlier one's log and a watcher polling the shared filename reads a stale or foreign log indefinitely (a watcher kept polling a deleted pod's progress.log for its full budget, all lines frozen at one timestamp). Give each pod's uploads a per-pod prefix or subdir (`out/<podname>/progress.log`) and key the watcher on an artifact only that pod writes; a poll line whose timestamp never advances is the tell to re-fetch a different path. If per-pod paths can't be used, fingerprint the SHARED log for the pod's pinned commit SHA (have the bootstrap echo `git rev-parse HEAD` into progress.log) and make the watcher ignore DONE/FAILED markers unless the SHA matches — the previous pod's terminal log lingers in the repo and a naive marker-match breaks the watcher on a stale verdict while the new pod is still mid-run.

## Pods

- **Preflight ANY paid-GPU spend with a design consult BEFORE the action — not just first pod launches** (`claude -p`, --allowedTools Read, --max-turns 20, neutral infra framing): new pod bootstraps AND worker-image rebuild/redeploy cycles AND any other action that bills. Hand it the deploy script/change and ask for what else will break in order of likelihood plus the minimal in-pod smoke (clone `-b <branch>` has the runner file; `import transformers, huggingface_hub` works; one `hf_hub_download` succeeds). One five-launch pod incident had five distinct, all-catchable-by-review failures (UA ban, unwritable repo namespace, default-branch clone, broken downloader pins, restart-loop confusion); review-first is the cheap end of that trade. Same class as experiment-design consults: if it declines on scope, record the decline and move on.
- Create via `runpodctl pod create --image ... --gpu-id "<full name>" --ports "8000/http" --env '{...}'`. Delete stopped/unused pods immediately — running pods bill by the hour even if the container never serves.
- A pod failing to start ("There are not enough free GPUs on the host machine") is host-specific: resume won't fix it; create a new pod (possibly a different GPU class) rather than retrying. Same rule for a host whose CUDA stack is broken INSIDE the container (torch sanity fails with 'CUDA unknown error ... devices to be zero' while the GPU is nominally attached): put a `torch.cuda.is_available()` assert in the boot BEFORE any work so it dies in the first minute, then delete and relaunch — on COMMUNITY hosts this is common enough that SECURE is the pragmatic next try. CUDA-sanity passing does NOT verify the RUNNER uses the GPU: a runner whose device line falls back (`mps/cpu` checks without a `cuda` branch, or `to("cpu")` typos) passes the boot assert and grinds the whole battery on CPU ~20-40x slower with zero errors — add a timed pace gate to the boot (generate ~40 tokens with the actual model, assert GPU-plausible seconds, log FAILED on breach) AND check the first completed cell's pace against the local MPS baseline before leaving the pod unattended. Exception: when the pod holds the only copy of artifacts on its volume, a patient resume-retry loop (10-20 attempts, 4-5 min apart) is worth the ~1 hr — hosts free up, and resume preserves the volume where a new pod gets a fresh one.
- `runtime.uptimeInSeconds` and REST-reported state can lag or show `None` while the pod actually works — the user's web console is the source of truth. Don't kill a pod on API state alone; ask the user to glance at the console first. When REST `GET /v1/pods/<id>` returns runtime null, the GraphQL pods query still reports liveness: `query { myself { pods { id name runtime { uptimeInSeconds } } } }` (send Content-Type: application/json or the GraphQL endpoint CSRF-rejects with a content-type error, NOT an auth failure); a non-null runtime with uptime means the container is genuinely up even while the proxy still 404s.
- A pod that holds the ONLY copy of artifacts and is GPU-starved: run a
  patient resume-retry loop (10-20 attempts, 4-5 min apart) — hosts free up,
  and a resume is the only way back to that host-local volume. Verify first
  that the volume is actually host-local (no networkVolumeId on the pod): a
  network volume can be re-attached to a fresh pod instead, which is faster
  than waiting out a starved host.
- A pod that auto-stopped from balance exhaustion mid-run does NOT keep its
  progress: the resume may boot with a CLEAN /workspace and re-run everything
  from scratch. The boot script being idempotent (skip-if-exists on adapters,
  datasets fetched fresh) is what makes that survivable — design boots so a
  full re-run is always safe, and treat 'check the balance BEFORE a long run'
  as part of the pre-flight (GraphQL clientBalance; a run that outlives the
  balance gets killed at the worst moment).
- Treat a pod's volume as EPHEMERAL for artifacts: pull weights, eval JSONs and anything valuable off the pod (through the boot's http.server tree over the proxy) THE MOMENT they are written — a balance dip or host eviction stops the pod, and a resumed pod does NOT reliably bring the volume contents back (a resume after a balance-exhaustion stop was observed booting with a clean /workspace and retraining from scratch). `desiredStatus: EXITED` with a 404 proxy means exactly that: nothing is reachable until a resume lands.
- Container stdout is readable with `runpodctl pod logs <id>` (JSON lines, `source:container` vs `source:system`) — read it BEFORE debugging blind through proxy 404s. When the boot script's own http.server serves only a subdirectory, symlink high-value logs (`pip.log`, `env.txt`, `progress.log`) into the served tree so the proxy can fetch them.
- A boot script that clones the repo runs whatever is on the BRANCH — commit and push new scripts before deploying the pod, or the pod clones without them and every step fails with FileNotFound.
- PATCHing `dockerStartCmd`/`env` on a RUNNING pod does NOT reliably restart the container (the proxy can sit at 'Waiting for service' forever while the pod bills). To change the boot script: delete the pod and create a fresh one — PATCH is only for fields that don't need a process restart.
- 'Disk quota exceeded' on `git clone` into /workspace means the VOLUME is full, not that the repo is big: volumes persist and accumulate prior sessions' HF caches, and a bf16 fetch (~2 bytes/param — 32B ≈ 65GB) blows past a small volume. Size volumeInGb for the largest model fetch (bf16 needs ~2x the params in bytes), and check `runpodctl pod logs` for quota lines before suspecting the clone.
- A pod whose SSH port times out on BOTH the public IP (portMappings) and the `<pod>-<port>.proxy.runpod.net` hostname while REST/GraphQL still report it RUNNING is a wedged container, not a network problem — stop the pod and resume it to force a fresh container. Force `-4` on ssh to the proxy hostname (it resolves AAAA first and v6 times out). The resume itself can hit host GPU starvation ('not enough free GPUs'); that is the retry-loop case, not a dead pod — the resume-retry pattern above applies.

## Serverless

Invoke: POST `https://api.runpod.ai/v2/<endpoint>/run` with `{"input": {...}}`. Create templates/endpoints via REST (`isServerless: true` on template create; read back every field — some create-body values are silently ignored). Always-on rules: PATCH flashboot=false after every endpoint create (the create body ignores it); PATCH containerDiskInGb to 80-100GB before the first cold boot when the worker downloads weights; flip private GHCR packages to public once in the console or pulls fail `unauthorized`; after any template/env change, recycle workers (workersMax 0→1) and let /health show a ready worker BEFORE submitting the test — jobs that race the recycle land on the old image and fail with the old bug. Full stale-code, debug, PeftModel-adapter, and GHCR/LFS pitfalls live in [references/serverless-worker-pitfalls.md](references/serverless-worker-pitfalls.md) — read it before iterating on a worker image or debugging a failing endpoint.

- Endpoint-create schema drift: `POST /v1/endpoints` rejects keys that older docs use (`gpuIds`, `executionTimeout`, `volumeMountPath`, `scalerIntervalSec` all bounce; it wants `executionTimeoutMs` at most). Enumerate the live schema instead of guessing: POST a minimal `{"name": ...}` and read the validation error (it names the required keys), then add fields one at a time and drop each one that bounces. A bare `name` + `templateId` + `workersMin`/`workersMax` + `idleTimeout` + `flashboot` create is accepted, and RunPod auto-assigns a cheap GPU class list — fine for a small model; pass nothing gpu-shaped rather than fighting the schema.
- The GHCR public flip is a console click, not an agent API call: `gh`'s default token has no `packages` scope (listing 403s, PATCH 404s), so don't burn cycles on `gh api` — hand the operator the package URL and wait for confirmation BEFORE creating the endpoint, or the first worker boots as a cached corpse on the unauthorized pull (recycle with workersMax 0→1 after the flip if it already did).
- Setting a relay service's env from an UNLINKED checkout: `railway variables --set K=V --project <project-id> --environment <env-id> --service <service>` works without `railway link` — pull the three ids out of the repo's deploy workflow yml (the CI deploy block names all of them) instead of hunting for a linked checkout.

## Model ↔ GPU sizing

Pick the MODEL first, then size for it (user prefers cost-effective open-weight; persona serving prefers pre-quantized 70B bnb-4bit on a 48GB card). Price/VRAM table, VRAM rules, and the GPTQ/AWQ/numpy/torch version matrices live in [references/sizing-and-versions.md](references/sizing-and-versions.md).

## Cost shape

- Shipping private data (corpora, adapters, non-committed files) into a fresh pod, in order of preference: (1) base64 into the boot script when <~100KB; (2) a PRIVATE HF DATASET REPO for anything bigger — upload locally with `huggingface_hub.HfApi(token=...).upload_file()` (raw REST PUT/multipart to the commit endpoint fails; the Python client is the working path), then pull on the pod with `hf_hub_download(repo_id, filename, repo_type="dataset", token=$HF_TOKEN)`. HF is reliably reachable from RunPod hosts; catbox.moe is NOT — RunPod egress to catbox dies with 'Remote end closed connection', so a catbox-based boot loop retries forever while the pod bills. Do not reuse another thread's active job repo; create a fresh one per purpose and delete it when the work ships. (3) quick tunnel (`cd <dir> && python3 -m http.server 8099 &` + `cloudflared tunnel --url http://localhost:8099`) for live data. Every fetch step MUST retry (3-5 attempts with sleep) AND verify content (min size + expected files after extract). A LAN-only ip is NOT reachable from the pod (CGNAT); the tunnel is the only route. Fetch the payload once locally before deploying to confirm it serves.
- The `pytorch/pytorch:*-runtime` images have NO `curl` and no `wget` — a boot script that shells out to curl for its payload fetch dies on 'command not found' while the container restart-loops (uptime resets every ~60s in the GraphQL pods query is the tell). Use `python3 -c 'import urllib.request; ...'` or `urlretrieve` for every download in boot scripts on these images.

- Cold start with a bootstrap-from-tarball approach is 10-15 min (apt+pip from scratch) — unusable for interactive UX. Baking deps into a pushed image drops it to ~60-90s (model load only); FlashBoot becomes viable again once the image is clean. Swapping the model DOWN from 14B→8B class (or any model change) invalidates this math: a new bake means a new tag, a fresh template, and the endpoint's model-reference updated or removed — a leftover model-reference from the old model silently pre-caches gigabytes the worker never loads and can fill the container disk (watch the 'Not enough free disk space' HF warnings in serverless logs).
- RunPod availability is spotty; keep a fallback order and SWEEP it programmatically rather than by hand: loop create attempts across GPU classes (48GB tier: A40 → RTX 6000 Ada → A6000 → L40S — the whole tier can go dry at once in the evening, and L40S is often the last one standing) × cloud type (SECURE then COMMUNITY) with a 2-minute sleep between full passes; give up after ~6 passes. A single 'There are no instances currently available' or 'no longer any instances available' response is a pool condition, not a config error — do not debug the request body on the first failure. Design the workload to tolerate worker death: scale-to-zero, stateless jobs, reconnecting clients.
- Live billing IS queryable: GraphQL `query { myself { clientBalance currentSpendPerHr spendLimit } }` against `api.runpod.io/graphql` returns balance, burn rate, and spend limit — enough to compute hours-left and alert before the account dies. Cross-check with `GET /v2/<endpoint>/health` worker counts to attribute the burn (a warm worker with zero traffic is the usual suspect).
- Cost anatomy for an always-on serving stack, largest line first: (1) a serverless endpoint with workersMin >= 1 bills a warm worker 24/7 regardless of traffic — one 48GB card is ~$19/day of pure standby; set workersMin 0 when the client can tolerate a 30-60s cold start from a cached volume, and scale it back up only for traffic windows. (2) EXITED pods keep billing their volume storage (volumes are separate from pod life); `GET rest.runpod.io/v1/pods` shows all statuses with `volumeInGb` — terminate pods whose results are committed, don't just stop them. (3) endpoints with stale queued jobs and idle min-workers are idle spend. Deriving where the money goes needs all three in one view: balance rate (GraphQL) + pod list with volumes + endpoint health worker counts.
- After any GPU incident, delete the pod/endpoint before walking away — a stuck "RUNNING" pod bills even with no working container. (Balance-exhaustion stops, volume ephemerality across resume, and host-starvation fallbacks are covered in the Pods section above.)
